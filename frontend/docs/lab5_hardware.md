# Расчёт аппаратных требований

Расчёт относится к итоговой системе «Масштаб», а не к Vite dev server. Сценарные допущения для учебной оценки: 50 пользователей, по 2 опубликованные карточки издержек в рабочий день, 8 часов работы, 250 рабочих дней в году, хранение 5 лет. Для одной карточки: POST создания (1), GET черновика (1), PUT публикации (1), GET списка (1), GET ленты (6), POST лайков (6), итого 16 запросов. Статические медиа оцениваются отдельно по диску; это не нагрузочный тест.

1. Средняя нагрузка: RPS = (50 × 2 × 16) / (8 × 60 × 60) = 0,0556 запроса/с. При коэффициенте пиков 10: RPSпик = 0,0556 × 10 = 0,556 запроса/с. Вход один раз в день добавляет 50 / 28800 = 0,00174 запроса/с, существенно результат не меняет.
2. Предположив производительность 20 запросов/с на ядро: N = ceil(0,556 / 20) = 1. Для совместного размещения API и трёх хранилищ принимаем минимум 2 ядра. RAM = 2 × 4 = 8 ГБ. Производительность 20 запросов/с — явное проектное допущение, перед промышленным запуском нужна нагрузочная проверка.
3. За 5 лет: Nкарточек = 50 × 2 × 250 × 5 = 125000. Размер строки costs: два INTEGER ID 8 Б; cost_name VARCHAR(100) до 400 Б UTF-8; cost_description VARCHAR(500) до 2000 Б; cost_status VARCHAR(10) до 10 Б ASCII; два URL VARCHAR(500) по 500 Б ASCII; cost_behavior VARCHAR(16) до 16 Б ASCII; cost_code INTEGER 4 Б; два TIMESTAMPTZ по 8 Б. Полезные данные: 8 + 400 + 2000 + 10 + 1000 + 16 + 4 + 16 = 3454 Б. Служебные данные и выравнивание оцениваем 64 Б, итого 3518 Б/строку. Это бюджет, а не точное pg_column_size.
4. На карточку предусматриваем 6 лайков: cost_likes содержит три INTEGER по 4 Б и около 28 Б служебных данных, 40 Б/строку. Вместе с резервом 160 Б на индексы costs и 64 Б на индексы каждой строки лайка: 125000 × (3518 + 160 + 6 × (40 + 64)) = 537750000 Б ≈ 0,501 ГиБ. Пользователи: 50 × (4 + 200 + 255 + 64) = 26150 Б. Redis: бюджет 50 × 512 = 25600 Б на активные сессии.
5. S3 на карточку: изображение 2 МиБ + видео 8 МиБ = 10485760 Б. За 5 лет: 125000 × 10485760 = 1310720000000 Б ≈ 1,192 ТиБ. Это целевой средний размер медиа для планирования, не размер fixture и не ограничение загрузки API. Логическое удаление место не освобождает, поэтому все карточки включены.
6. Основной диск: (1310720000000 + 537750000 + 26150 + 25600 + 20 × 1073741824) × 1,3 ≈ 1,733 ТБ. Принимаем 2 ТБ SSD; резервная копия на отдельном хранилище — ещё не менее 2 ТБ. Итог: 2 ядра, 8 ГБ RAM, 2 ТБ SSD + отдельное хранилище резервных копий. Клиент: современный браузер, 4 ГБ RAM; это минимальное проектное требование, не результат измерения.
